Complete Guide to Rendering in React.js and Next.js
Rendering is one of the most important concepts in React and Next.js. If you understand rendering properly, many other concepts will become much easier:
- React Virtual DOM
- Real DOM
- Reconciliation
- React Fiber Architecture
- SSR (Server-Side Rendering)
- CSR (Client-Side Rendering)
- SSG (Static Site Generation)
- ISR (Incremental Static Regeneration)
- Hydration
- Server Components
- Client Components
- Streaming
- Suspense
- Partial Prerendering
- React Server Component Payload (RSC)
- SEO and performance optimization
I'll explain these concepts from the fundamentals, using examples from your existing React and Next.js learning.

We'll also compare React.js and Next.js so you understand what happens behind the scenes.
PART 1: What is Rendering?
1.1 What does rendering mean?
Rendering means converting your application code into something that can be displayed on the screen.

For example, consider this React component:
function App() {
    return (
        <div>
            <h1>Hello World</h1>
            <p>Welcome to React</p>
        </div>
    );
}

export default App;

You write JSX, but the browser doesn't directly understand JSX.

The browser understands:
- HTML
- CSS
- JavaScript
So React and its rendering system process your component and create the necessary browser DOM elements.

Eventually, the browser displays:

Hello World

Welcome to React

This entire process is broadly called rendering.
Simple example from PHP
Since you've worked with Core PHP and Laravel, let's compare.

In PHP:
<?php

$name = "Haris";

?>

<h1>
    Welcome <?php echo $name; ?>
</h1>

PHP executes on the server and generates HTML:
<h1>Welcome Haris</h1>

The browser receives the HTML and displays it.

In React:
function App() {
    const name = "Haris";

    return <h1>Welcome {name}</h1>;
}

React executes the component and works with the browser DOM to display the result.

The important difference is that React also manages subsequent UI updates when application state changes.
PART 2: What is DOM?
Before understanding React rendering, you must understand DOM.
2.1 DOM stands for Document Object Model
DOM is a programming interface that represents an HTML document as a tree of objects.

Whenever a browser receives HTML, it parses that HTML and creates a DOM tree.

Consider this HTML:
<!DOCTYPE html>
<html>
    <head>
        <title>My Website</title>
    </head>

    <body>
        <div id="root">
            <h1>Hello World</h1>
            <p>Welcome to my website</p>
        </div>
    </body>
</html>

The browser creates a structure similar to this:
Document
   |
   HTML
   |
   |------ HEAD
   |         |
   |         TITLE
   |
   |------ BODY
             |
             DIV (#root)
                |
                |------ H1
                |        |
                |        Hello World
                |
                |------ P
                         |
                         Welcome to my website

This is called the DOM tree.

Every HTML element becomes a node in this tree.

For example:
document.getElementById("root");

This JavaScript accesses the DOM element.

You can also modify it:
const heading = document.querySelector("h1");

heading.innerText = "Updated Heading";

The browser updates the displayed content.
2.2 Types of DOM nodes
Some common DOM node types are:
Node type	Example
Document	Entire HTML document
Element	<div>, <h1>, <p>
Text	Text inside an element
Attribute	id, class, src
Comment	<!-- comment -->


2.3 What happens when DOM changes?
Suppose you have:
<h1>Hello</h1>

You update it using JavaScript:
document.querySelector("h1").innerText = "Welcome";

The browser updates the DOM.

However, DOM changes can cause additional browser work.

The browser may need to perform:
1. Style calculation.
2. Layout calculation.
3. Painting.
4. Compositing.
Let's understand these.

Style calculation

The browser calculates which CSS styles apply to each element.

Layout

The browser calculates the position and dimensions of elements.

For example:
- Height
- Width
- Margin
- Padding
- Position
Painting

The browser paints pixels, including text, borders, backgrounds and shadows.

Compositing

The browser combines different visual layers to produce the final screen.

These are important browser rendering concepts, but remember:

React rendering and browser rendering are not exactly the same thing.

React calculates what the UI should look like. The browser handles displaying it.
PART 3: What is Virtual DOM?
Now we are getting to one of React's most important concepts.
3.1 What is Virtual DOM?
Virtual DOM is a lightweight, in-memory representation of the UI that React uses to manage updates.

It represents the UI structure using JavaScript objects rather than directly modifying the browser DOM during the component render phase.

For example:
function App() {
    return (
        <div>
            <h1>Hello World</h1>
            <p>Welcome</p>
        </div>
    );
}

Conceptually, React maintains a representation resembling:
{
    type: "div",
    props: {
        children: [
            {
                type: "h1",
                props: {
                    children: "Hello World"
                }
            },
            {
                type: "p",
                props: {
                    children: "Welcome"
                }
            }
        ]
    }
}

This is a simplified illustration, not the exact internal structure React uses.

React uses its internal Fiber data structures to represent and manage component work.
3.2 Why does React use Virtual DOM?
Imagine you have a website containing:
<div>
    <h1>My Shop</h1>

    <p>Price: $100</p>

    <button>Add to Cart</button>
</div>

Suppose the price changes from $100 to $120.

With manual JavaScript, you might do:
document.querySelector("p").innerText = "Price: $120";

You are responsible for finding and modifying the correct DOM element.

In React, you simply update state:
import { useState } from "react";

function Product() {
    const [price, setPrice] = useState(100);

    return (
        <div>
            <h1>My Shop</h1>

            <p>Price: ${price}</p>

            <button onClick={() => setPrice(120)}>
                Update Price
            </button>
        </div>
    );
}

React handles the UI update.

You don't manually find the paragraph and change its content.

React determines what changed and updates the necessary DOM elements.

Important: Virtual DOM is not automatically faster than every possible direct DOM operation. Its main benefit is declarative UI management and efficient, coordinated updates.
PART 4: How React Rendering Actually Works
This is probably the most important section.

React uses a process commonly explained through three main stages:
1. Trigger
2. Render
3. Commit
Let's understand each stage.
4.1 Stage 1: Triggering a render
A React component generally renders for two reasons:

Reason 1: Initial rendering

When your application starts, React performs the initial render.

Example:
import { createRoot } from "react-dom/client";

import App from "./App";

createRoot(document.getElementById("root")).render(
    <App />
);

React starts rendering the application.

Reason 2: State changes

Whenever you update state, React schedules an update.

Example:
import { useState } from "react";

function Counter() {

    const [count, setCount] = useState(0);

    return (
        <div>
            <h1>{count}</h1>

            <button onClick={() => setCount(count + 1)}>
                Increase
            </button>
        </div>
    );
}

export default Counter;

Initially:
count = 0

You click the button.
setCount(count + 1);

Now React schedules another render with the updated state.

One important point: updating state does not mean React immediately modifies the DOM. It schedules the rendering work.
4.2 Stage 2: Render phase
During this phase, React calls your components to determine what the UI should look like.

For example:
function Counter() {

    const [count, setCount] = useState(0);

    return <h1>{count}</h1>;
}

Initially, the component produces:
<h1>0</h1>

After clicking:
<h1>1</h1>

React calculates the difference between the previous and next UI representations.

At this point, React is calculating the changes. It hasn't committed those changes to the DOM yet.

Also, React may render a component without actually changing any DOM elements.

For example, if the resulting UI is the same, no DOM update may be necessary.
Important concept: Re-rendering is not the same as DOM updating.
This is a common misunderstanding among React beginners.

A component can re-render without causing a DOM change.
4.3 Stage 3: Commit phase
After calculating the required changes, React commits them to the actual browser DOM.

For example:

Previous DOM:
<h1>0</h1>

New UI:
<h1>1</h1>

React updates the necessary DOM content.

The resulting DOM:
<h1>1</h1>

React doesn't need to recreate the entire page.

It updates the required part.
Complete flow
User clicks button
        |
        v
setCount(count + 1)
        |
        v
React schedules update
        |
        v
RENDER PHASE
        |
        |-- Calls component
        |-- Calculates new UI
        |-- Reconciles changes
        |
        v
COMMIT PHASE
        |
        |-- Updates necessary DOM nodes
        |
        v
Browser paints updated UI

The official React documentation explains these stages in detail.

PART 5: Which Algorithm Does React Use?
Now let's discuss an important advanced concept.

React uses Reconciliation, supported by its Fiber architecture, to manage UI updates.

There are two terms you should understand:
1. Reconciliation algorithm
2. Fiber architecture
They are related, but they are not the same thing.
5.1 What is Reconciliation?
Reconciliation is the process React uses to compare the previous UI representation with the new UI representation and determine what changes are necessary.

Let's take an example.

Previous UI:
function App() {
    return (
        <div>
            <h1>My Shop</h1>
            <p>Price: $100</p>
        </div>
    );
}

New UI:
function App() {
    return (
        <div>
            <h1>My Shop</h1>
            <p>Price: $200</p>
        </div>
    );
}

What changed?

Only the price.

React determines that:
- The div is still the same type.
- The h1 is still the same type.
- The p is still the same type.
- The text inside the p changed.
Therefore, React only needs to update the paragraph's text.

This comparison and update process is called reconciliation.
5.2 How does React compare elements?
React uses heuristics to make reconciliation efficient.

Some important rules:
Rule 1: Different element types
Previous:
<div>Hello</div>

New:
<section>Hello</section>

Since the element type changed, React generally destroys the old subtree and creates a new one.
Rule 2: Same element type
Previous:
<div className="old">
    Hello
</div>

New:
<div className="new">
    Hello
</div>

React can reuse the existing DOM element and update its class.
Rule 3: Lists and Keys
This is extremely important.

Consider:
const users = [
    { id: 1, name: "Ali" },
    { id: 2, name: "Ahmed" },
    { id: 3, name: "Haris" }
];

Rendering:
function Users() {

    return (
        <ul>
            {users.map(user => (
                <li key={user.id}>
                    {user.name}
                </li>
            ))}
        </ul>
    );
}

Why do we use key?

Imagine the original list:
Ali
Ahmed
Haris

Now you insert a new user at the beginning:
Usman
Ali
Ahmed
Haris

Without stable keys, React has less information to match the previous list elements with the new ones.

With stable keys:
key={user.id}

React can identify which item was inserted and which existing items were retained.

Important: Keys should be stable and unique among siblings. Avoid using array indexes when list items can be inserted, deleted or reordered.
5.3 What is Fiber Architecture?
Fiber is React's internal architecture for managing rendering work.

Before Fiber, React's reconciliation work was largely synchronous and recursive.

This could become problematic for complex applications because rendering work could block the main thread.

Fiber introduced a more flexible architecture.

It allows React to:
- Break rendering work into smaller units.
- Prioritize updates.
- Pause and resume rendering work.
- Abandon outdated rendering work.
- Schedule updates according to priority.
For example:

Imagine your application has:
- A large product list.
- A search box.
- A shopping cart.
- Animations.
When the user types something in the search box, React should prioritize keeping the interface responsive.

Fiber's scheduling capabilities help React manage such work.
Fiber architecture simplified
React Application
       |
       v
Fiber Architecture
       |
       v
Reconciliation
       |
       |-- Compare previous UI
       |-- Calculate new UI
       |-- Schedule work
       |
       v
Commit Phase
       |
       v
Real DOM

What is the difference?
Concept	Meaning
Virtual DOM	Conceptual representation of UI
Reconciliation	Determines what needs to change
Fiber	Internal architecture for managing rendering work
Commit	Applies necessary changes to the DOM
DOM	Actual browser document structure


Important interview point:

React does not simply compare two complete HTML documents. It uses a heuristic reconciliation process with Fiber to efficiently manage updates.
PART 6: What are Different Rendering Types?
Now let's move to the most important topic for Next.js.

There are several rendering strategies used in modern web development.

The main ones are:
1. CSR – Client-Side Rendering
2. SSR – Server-Side Rendering
3. SSG – Static Site Generation
4. ISR – Incremental Static Regeneration
Other related concepts include:
5. Streaming SSR
6. Dynamic Rendering
7. Static Rendering
8. Partial Prerendering
9. Hybrid Rendering
Let's understand each one.
7. CSR – Client-Side Rendering
CSR stands for Client-Side Rendering.

It means that the browser executes JavaScript to render the application UI.

React applications created with Vite commonly use CSR by default.
7.1 How CSR works
Imagine you create a React project using Vite.
npm create vite@latest my-app

Your application has:
function App() {

    return (
        <div>
            <h1>Welcome to My Website</h1>
            <p>This is a React application.</p>
        </div>
    );

}

export default App;

When the browser visits your website, the process looks like this:

Step 1: Browser sends a request
Browser
   |
   | Request website
   v
Server

Step 2: Server sends basic HTML

The server might return something like:
<!DOCTYPE html>
<html>
<head>
    <title>My React App</title>
</head>
<body>

    <div id="root"></div>

    <script type="module" src="/src/main.jsx"></script>

</body>
</html>

Notice something important.

The root div is empty.
<div id="root"></div>

Step 3: Browser downloads JavaScript

The browser downloads your React JavaScript files.

Step 4: React executes

React executes:
function App() {
    return <h1>Welcome to My Website</h1>;
}

Step 5: React creates DOM elements

React inserts the required elements into the root div.

Now the user sees:
<div id="root">
    <h1>Welcome to My Website</h1>
</div>

CSR flow
User visits website
        |
        v
Browser requests HTML
        |
        v
Server sends basic HTML
        |
        v
Browser downloads JavaScript
        |
        v
JavaScript executes
        |
        v
React renders components
        |
        v
DOM gets updated
        |
        v
User sees the UI

7.2 Advantages of CSR
- Excellent for highly interactive applications.
- Smooth navigation after initial loading.
- Less server-side rendering work.
- Easy integration with APIs.
- Suitable for dashboards and admin panels.
7.3 Disadvantages of CSR
- Initial rendering may take longer.
- Users might initially see an empty page or loading screen.
- Search engine crawlers may have to execute JavaScript to discover content.
- Large JavaScript bundles can affect performance.
Modern search engines can execute JavaScript, so CSR does not automatically mean poor SEO. However, server-rendered HTML generally provides a more reliable initial content experience.
7.4 CSR example in React
import { useEffect, useState } from "react";

function Products() {

    const [products, setProducts] = useState([]);

    const [loading, setLoading] = useState(true);

    useEffect(() => {

        fetch("/api/products")
            .then(res => res.json())
            .then(data => {
                setProducts(data);
                setLoading(false);
            });

    }, []);

    if (loading) {
        return <h2>Loading Products...</h2>;
    }

    return (
        <div>
            <h1>Products</h1>

            {products.map(product => (
                <h3 key={product.id}>
                    {product.name}
                </h3>
            ))}
        </div>
    );

}

export default Products;

Here:
1. React initially renders the loading message.
2. useEffect runs in the browser.
3. The browser requests products.
4. State updates.
5. React renders the products.
This is a typical CSR data-fetching pattern.
8. SSR – Server-Side Rendering
SSR stands for Server-Side Rendering.

It means the server generates HTML for a page when a request arrives.

Instead of waiting for the browser to execute all the application JavaScript before showing content, the server sends already-rendered HTML.
8.1 How SSR works
Imagine you have an ecommerce website.

A user visits:
https://example.com/products/iphone-17

The server receives the request.

It fetches product information from the database:
{
    name: "iPhone 17",
    price: 799,
    description: "Latest Apple smartphone"
}

The server renders the page into HTML.

Example:
<div>
    <h1>iPhone 17</h1>

    <h2>$799</h2>

    <p>Latest Apple smartphone</p>
</div>

The browser receives this HTML and can display the content before React finishes hydration.
SSR flow
User visits website
        |
        v
Browser sends request
        |
        v
Server receives request
        |
        v
Server fetches data
        |
        v
React renders HTML
        |
        v
Server sends HTML
        |
        v
Browser displays content
        |
        v
JavaScript downloads
        |
        v
Hydration happens
        |
        v
Page becomes interactive

Notice that the server generates the HTML.

The browser still executes JavaScript for interactive components.

This brings us to hydration, which we'll cover shortly.
8.2 SSR in Next.js
In the Next.js App Router, you can create a server-rendered page using a Server Component.

For example:

app/products/page.jsx
async function getProducts() {

    const response = await fetch(
        "https://api.example.com/products",
        {
            cache: "no-store"
        }
    );

    return response.json();
}

export default async function ProductsPage() {

    const products = await getProducts();

    return (
        <div>
            <h1>Products</h1>

            {products.map(product => (
                <div key={product.id}>
                    <h2>{product.name}</h2>
                    <p>${product.price}</p>
                </div>
            ))}
        </div>
    );
}

Here:
cache: "no-store"

means Next.js should not reuse a cached response for this fetch.

The data is requested when the page is rendered for a request.

This is a common way to implement request-time dynamic data fetching.
When should you use SSR?
Use SSR when:
- Data changes frequently.
- You need request-specific information.
- You need personalized pages.
- You need fresh data on every request.
- You need server-generated HTML.
Examples:
- User dashboards.
- Order tracking.
- Live product inventory.
- Personalized account pages.
- Financial information.
Important: SSR does not automatically mean every component must execute on the client. Next.js Server Components can render on the server, and Client Components can be hydrated separately.
9. SSG – Static Site Generation
SSG stands for Static Site Generation.

It means HTML pages are generated in advance, generally during the build process.

Instead of generating HTML every time someone visits the page, Next.js creates the HTML before users request it.
9.1 How SSG works
Imagine you have a blog website.

Your blog contains:
/blog/react-introduction
/blog/nextjs-introduction
/blog/javascript-basics

These blog articles don't change frequently.

It would be unnecessary to generate their HTML every time someone visits them.

Instead, Next.js can generate the HTML during the build.
SSG flow
Developer runs build
        |
        v
Next.js executes application
        |
        v
Fetches required data
        |
        v
Generates HTML pages
        |
        v
Stores generated output
        |
        v
Website deployed
        |
        v
User visits website
        |
        v
Server/CDN returns existing HTML

The HTML is already available.

The server doesn't need to execute the page's rendering logic for every visitor.
9.2 SSG example in Next.js
Consider:

app/blog/page.jsx
async function getBlogs() {

    const response = await fetch(
        "https://api.example.com/blogs",
        {
            cache: "force-cache"
        }
    );

    return response.json();
}

export default async function BlogPage() {

    const blogs = await getBlogs();

    return (
        <div>
            <h1>Latest Blogs</h1>

            {blogs.map(blog => (
                <article key={blog.id}>
                    <h2>{blog.title}</h2>
                    <p>{blog.description}</p>
                </article>
            ))}
        </div>
    );
}

Here:
cache: "force-cache"

allows the fetch result to be cached and reused.

When the route is eligible for static generation, Next.js can generate its HTML during the build.

The exact static/dynamic decision also depends on the route's other dependencies and the Next.js configuration.
9.3 Advantages of SSG
- Very fast page delivery.
- Excellent initial HTML availability.
- Good SEO foundations.
- Lower request-time rendering workload.
- Can be served through a CDN.
9.4 Disadvantages of SSG
- Data can become outdated.
- Content generally needs regeneration through a new build or revalidation.
- Generating huge numbers of pages during builds can increase build time.
When should you use SSG?
Examples:
- Blog websites.
- Documentation websites.
- About Us pages.
- Contact pages.
- Service pages.
- Landing pages.
- Company information pages.
For example, if you have a repair business website:
/about
/contact
/iphone-repair
/samsung-repair
/macbook-repair

These pages are excellent candidates for static generation if their content doesn't need to change on every request.
10. ISR – Incremental Static Regeneration
ISR stands for Incremental Static Regeneration.

This is one of Next.js's most useful features.

It combines the advantages of static generation with automatic content revalidation.

Let's understand the problem first.
10.1 Problem with SSG
Imagine you have an ecommerce website.

You generate product pages during the build.

Your product price is:
iPhone Price = $799

After two days, you update the database:
iPhone Price = $899

But your statically generated page still contains:
$799

Why?

Because SSG generated the page earlier.

You would need another build to generate updated HTML if you were relying only on build-time generation.

This is where ISR helps.
10.2 How ISR works
ISR allows Next.js to regenerate static content after a specified revalidation period.

For example:
export const revalidate = 60;

This tells Next.js to use a 60-second revalidation interval for the route.

Conceptually:
Page generated
       |
       v
Static HTML served
       |
       v
60 seconds pass
       |
       v
A new request arrives
       |
       v
Existing page may be served
       |
       v
Next.js revalidates in background
       |
       v
New HTML generated
       |
       v
Future requests receive updated content

The important detail:

Time-based revalidation does not necessarily regenerate the page at the exact moment 60 seconds pass.

It makes the page eligible for revalidation. A subsequent request can trigger regeneration.
10.3 ISR example in Next.js
app/products/page.jsx
export const revalidate = 60;

async function getProducts() {

    const response = await fetch(
        "https://api.example.com/products",
        {
            next: {
                revalidate: 60
            }
        }
    );

    return response.json();
}

export default async function ProductsPage() {

    const products = await getProducts();

    return (
        <div>
            <h1>Products</h1>

            {products.map(product => (
                <div key={product.id}>
                    <h2>{product.name}</h2>
                    <p>${product.price}</p>
                </div>
            ))}
        </div>
    );
}

Here:
next: {
    revalidate: 60
}

allows Next.js to revalidate the cached data after the specified interval.

The route-level configuration:
export const revalidate = 60;

sets the route's revalidation interval.

You can also use on-demand revalidation.

For example, after updating a product in your admin panel, you could tell Next.js to revalidate its product page.
import { revalidatePath } from "next/cache";

revalidatePath("/products");

This is useful when you want updated content without waiting for a time-based interval.
When should you use ISR?
Examples:
- Ecommerce product pages.
- Product categories.
- Blog articles.
- Business listings.
- Repair service pages.
- Public company websites.
For your repair widget or ecommerce projects, ISR can be particularly useful when product information changes occasionally but you still want fast page delivery.
PART 11: Comparison of CSR, SSR, SSG and ISR
Let's compare all four.
Feature	CSR	SSR	SSG	ISR
Full HTML generation	Browser	Server per request	Build time	Build time + regeneration
Rendering location	Browser	Server	Build environment	Build/background regeneration
Initial HTML content	Often minimal	Generated HTML	Generated HTML	Generated HTML
Fresh data	Client fetches	Per request	Build-time data until rebuilt	After revalidation
SEO	Requires JS execution for content	Good	Good	Good
Server workload	Less rendering work	Higher per-request work	Low per-request work	Generally low
Best for	Dashboards	Personalized data	Static websites	Occasionally updated content


Real-world example
Imagine you are building a repair business website.
Page	Suitable strategy	Reason
Homepage	SSG/ISR	Content changes occasionally
About Us	SSG	Mostly static
Contact	SSG	Mostly static
Blog	SSG/ISR	Articles change occasionally
Product details	ISR	Product information changes
Live inventory	SSR or CSR	Needs fresh information
Customer dashboard	SSR/CSR	Personalized information


One important thing:

You don't have to use only one rendering strategy throughout your website.

Modern Next.js applications can combine multiple strategies.

This is called hybrid rendering.
PART 12: What is Hydration?
Now let's understand one of the most confusing React and Next.js concepts.

Hydration is the process through which React connects JavaScript functionality to HTML that has already been generated on the server.

In simple words:

The server sends HTML, the browser displays it, and React makes the relevant parts interactive by hydrating them.

Let's understand with an example.
12.1 Without hydration
Imagine your server sends this HTML:
<div>
    <h1>Welcome</h1>

    <button>Click Me</button>
</div>

The browser can display:

Welcome

[Click Me]

But simply receiving HTML doesn't automatically provide React's event-handling functionality.

The button is just an HTML button at this stage.
12.2 With hydration
Now suppose you have this React component:
"use client";

import { useState } from "react";

export default function Counter() {

    const [count, setCount] = useState(0);

    return (
        <div>
            <h1>Count: {count}</h1>

            <button onClick={() => setCount(count + 1)}>
                Increase
            </button>
        </div>
    );
}

The server can generate initial HTML resembling:
<div>
    <h1>Count: 0</h1>

    <button>Increase</button>
</div>

The browser displays it.

PART 13: What is Hydration Mismatch?
This is another important concept, especially when working with Next.js.

A hydration mismatch happens when the HTML generated by the server doesn't match what React expects during the initial client render.

Let's understand.

Consider:
"use client";

export default function Home() {

    return (
        <h1>{Math.random()}</h1>
    );

}

Imagine the server renders:
<h1>0.12345</h1>

But when the browser initially renders the component, it generates:
<h1>0.67891</h1>

These values are different.

React expected the server HTML and initial client output to match, but they don't.

This can produce a hydration error.
Common causes
1. Using Math.random() during rendering
Math.random()

It can generate different values on the server and client.

2. Using Date.now()
Date.now()

The server and client may execute it at different times.

3. Accessing browser-only APIs
window.innerWidth

The server doesn't have the browser's window object.

4. Accessing localStorage during initial rendering
localStorage.getItem("theme");

localStorage is available in the browser, not on the server.
How to fix it?
For browser-only values, you can use useEffect.
"use client";

import { useEffect, useState } from "react";

export default function Home() {

    const [width, setWidth] = useState(0);

    useEffect(() => {

        setWidth(window.innerWidth);

    }, []);

    return (
        <h1>Screen Width: {width}</h1>
    );

}

Why does this work?
1. The server renders Screen Width: 0.
2. The initial client render also uses 0.
3. Hydration can match.
4. After hydration, useEffect runs.
5. The browser updates the width.
This is one of the most useful techniques when working with Next.js.
PART 14: Server Components vs Client Components
Now we are getting to the architecture of modern Next.js.

This is extremely important if you are learning the Next.js App Router.

First, understand that Server Components and Client Components are React component types.

They are not simply two different names for SSR and CSR.
14.1 What are Server Components?
Server Components are components that execute in a server environment.

They can:
- Fetch data directly from databases.
- Access server-side resources.
- Read files from the filesystem.
- Keep sensitive logic on the server.
- Render UI without sending their component implementation to the browser as client JavaScript.
In the Next.js App Router, components are Server Components by default.

Example:

app/products/page.jsx
async function getProducts() {

    const response = await fetch(
        "https://api.example.com/products"
    );

    return response.json();
}

export default async function ProductsPage() {

    const products = await getProducts();

    return (
        <div>
            <h1>Products</h1>

            {products.map(product => (
                <div key={product.id}>
                    <h2>{product.name}</h2>
                    <p>${product.price}</p>
                </div>
            ))}
        </div>
    );
}

Notice:
export default async function ProductsPage()

This is an asynchronous Server Component.

You can fetch data directly using await.

You don't need useEffect for this server-side data fetching.
Server Component advantages
1. Less client-side JavaScript.
2. Direct access to server-side resources.
3. Better separation of server and browser functionality.
4. Data fetching close to the data source.
5. Sensitive server-side implementation can remain on the server.
14.2 What are Client Components?
Client Components are components that use client-side React functionality.

For example:
- useState
- useEffect
- useReducer
- useContext
- Event handlers
- Browser APIs
- Interactive UI
In Next.js, you declare a Client Component using:
"use client";

This directive must appear at the top of the file, before imports.

Example:

app/components/Counter.jsx
"use client";

import { useState } from "react";

export default function Counter() {

    const [count, setCount] = useState(0);

    return (
        <div>
            <h1>Count: {count}</h1>

            <button onClick={() => setCount(count + 1)}>
                Increase
            </button>
        </div>
    );
}

Why do we need "use client"?

Because this component needs:
useState()

And it uses:
onClick={}

These require client-side React functionality.
Client Component advantages
- Supports state management.
- Supports event handlers.
- Supports React hooks such as useEffect.
- Supports browser APIs.
- Allows interactive UI.
PART 15: Server Components vs Client Components Comparison
Feature	Server Components	Client Components
Execution	Server environment	Browser environment for interactive rendering
Default in Next.js App Router	Yes	No
useState	No	Yes
useEffect	No	Yes
onClick	No	Yes
Browser APIs	No	Yes
Direct database access	Yes, when securely configured	No
Server secrets	Can access them securely	Must not contain them

Interactivity	No client-side interactivity by itself	Yes


Important clarification
Client Components can also be pre-rendered into HTML on the server during the initial page load.

This confuses many beginners.

For example:
"use client";

import { useState } from "react";

export default function Counter() {

    const [count, setCount] = useState(0);

    return <button onClick={() => setCount(count + 1)}>
        Count: {count}
    </button>;
}

Even though this is a Client Component, Next.js can generate its initial HTML on the server.

Then the browser hydrates it.

Therefore:

Client Component does not mean that the component is rendered only in the browser.

It means the component belongs to the client module graph and can use client-side React functionality.
PART 16: Can Server Components and Client Components Work Together?
Yes!

This is one of the most powerful features of Next.js.

Imagine an ecommerce product page.

You need:
- Product details.
- Product price.
- Product description.
- Add to Cart button.
- Quantity selector.
The product information can be handled by a Server Component.

The interactive shopping cart can be handled by a Client Component.
Example
Your folder structure:
app/
│
├── products/
│   └── page.jsx
│
└── components/
    ├── ProductDetails.jsx
    └── AddToCart.jsx

Server Component
app/products/page.jsx
import AddToCart from "../components/AddToCart";

async function getProduct() {

    const response = await fetch(
        "https://api.example.com/product/1"
    );

    return response.json();
}

export default async function ProductPage() {

    const product = await getProduct();

    return (
        <div>

            <h1>{product.name}</h1>

            <h2>${product.price}</h2>

            <p>{product.description}</p>

            <AddToCart productId={product.id} />

        </div>
    );
}

Client Component
app/components/AddToCart.jsx
"use client";

import { useState } from "react";

export default function AddToCart({ productId }) {

    const [quantity, setQuantity] = useState(1);

    function addToCart() {

        console.log({
            productId,
            quantity
        });

    }

    return (
        <div>

            <button onClick={() => setQuantity(quantity - 1)}>
                -
            </button>

            <span>{quantity}</span>

            <button onClick={() => setQuantity(quantity + 1)}>
                +
            </button>

            <button onClick={addToCart}>
                Add To Cart
            </button>

        </div>
    );
}

What happens here?
1. Next.js executes ProductPage on the server.
2. It fetches product information.
3. The product details are rendered.
4. Next.js processes the Client Component boundary.
5. The browser receives the generated HTML and the necessary React Server Component data.
6. The AddToCart component is hydrated.
7. The user can increase/decrease quantity and add products.
This is an example of combining Server Components and Client Components.
Recommended architecture
Product Page (Server Component)
             |
             |
       Fetch Product
             |
             v
       Product Details
             |
             v
      AddToCart (Client)
             |
             |-- useState
             |-- onClick
             |-- Quantity
             |-- Add to Cart

My recommendation: Keep components as Server Components by default. Convert only the components that genuinely need client-side interactivity.
PART 17: What is React Server Component Payload (RSC)?
This is an advanced concept related to Server Components.

RSC stands for React Server Components.

The RSC Payload is a special serialized representation of the Server Component tree that Next.js sends to the browser.

It contains information such as:
- Rendered Server Component output.
- References to Client Components.
- References to the JavaScript needed for Client Components.
- Props passed from Server Components to Client Components.
It is not simply HTML.
Example
Suppose you have:
export default function Page() {

    return (
        <div>
            <h1>Welcome</h1>

            <Counter />
        </div>
    );

}

Counter is a Client Component.

Next.js needs to coordinate:
1. Server Component output.
2. Client Component references.
3. Props passed between them.
4. Client Component hydration.
The RSC Payload helps coordinate this process.
Why is it useful?
It enables Next.js to:
- Separate server and client responsibilities.
- Send server-rendered component information.
- Avoid shipping unnecessary Server Component JavaScript.
- Support efficient client-side navigation.
- Update parts of the component tree without requiring a complete page reload.
Official reference: React Server Components
PART 18: What is Streaming SSR?
Streaming is another important rendering technique.

Normally, you might imagine the server waits until the entire page has finished rendering before sending the response.

But what if your page contains multiple sections and one section takes a long time to load?

For example:
Product Page
    |
    |-- Product Information (Fast)
    |
    |-- Product Reviews (Slow)
    |
    |-- Recommended Products (Slow)

Without streaming, the user might need to wait for all sections.

Streaming allows the server to send completed portions of the page as they become ready.
18.1 How streaming works
Server starts rendering
        |
        v
Product information ready
        |
        v
Send product information
        |
        v
Reviews still loading
        |
        v
Send reviews when ready
        |
        v
Recommendations ready
        |
        v
Send recommendations

This improves perceived loading performance.
18.2 Streaming example in Next.js
You can use React Suspense.

app/products/page.jsx
import { Suspense } from "react";

async function Reviews() {

    const response = await fetch(
        "https://api.example.com/reviews"
    );

    const reviews = await response.json();

    return (
        <div>
            <h2>Reviews</h2>

            {reviews.map(review => (
                <p key={review.id}>
                    {review.comment}
                </p>
            ))}
        </div>
    );
}

export default function ProductPage() {

    return (
        <div>

            <h1>iPhone 17</h1>

            <p>Price: $799</p>

            <Suspense fallback={<p>Loading Reviews...</p>}>
                <Reviews />
            </Suspense>

        </div>
    );
}

Here:
<Suspense fallback={<p>Loading Reviews...</p>}>

allows the rest of the page to be displayed while reviews are loading.

Next.js can stream the completed content to the browser.

You can also create:
app/
  products/
    page.jsx
    loading.jsx

loading.jsx:
export default function Loading() {

    return <h2>Loading Product Page...</h2>;

}

Next.js uses this as a loading UI for the route segment.
PART 19: What is Partial Prerendering (PPR)?
Partial Prerendering is an advanced rendering approach that combines static and dynamic content within a single page.

Imagine a product page.

Some content rarely changes:
- Header.
- Navigation.
- Product description.
- Footer.
Other content changes frequently:
- Live stock availability.
- Personalized offers.
- User-specific information.
With Partial Prerendering, Next.js can prepare a static shell and stream dynamic sections when the request arrives.
Conceptual example
PRODUCT PAGE
     |
     |-- STATIC SHELL
     |      |
     |      |-- Header
     |      |-- Product Description
     |      |-- Footer
     |
     |
     |-- DYNAMIC CONTENT
            |
            |-- Live Inventory
            |-- Personalized Offers

This combines fast initial delivery with dynamic content.

PPR and its configuration have evolved across Next.js versions, so check the documentation for the exact version you are using.

PART 20: Static Rendering vs Dynamic Rendering
These terms are also used in Next.js.

They describe how Next.js produces route output.
Static Rendering
The route is rendered ahead of the request, typically during build time or through later revalidation.

Example:
/about
/contact
/services

These pages don't need personalized information.
Dynamic Rendering
The route is rendered at request time when it depends on dynamic request information or uncached data.

For example:
import { cookies } from "next/headers";

export default async function Dashboard() {

    const cookieStore = await cookies();

    const token = cookieStore.get("token");

    return (
        <div>
            <h1>Dashboard</h1>
        </div>
    );
}

The route depends on request-specific cookies.

This is a common reason for dynamic rendering.
Important distinction
Static Rendering and SSG are closely related concepts.

Dynamic Rendering and request-time SSR are closely related concepts.

In modern Next.js, caching and rendering are more configurable than a simple four-category model suggests.

PART 22: What is Prefetching?
Prefetching means loading resources before they are actually needed.

Imagine a user is viewing your homepage.

You have this link:
<Link href="/products">
    Products
</Link>

Next.js can prefetch the destination route when the link becomes eligible for prefetching, such as when it enters the viewport.

Then, when the user clicks Products, some of the required resources may already be available.
Benefits
- Faster navigation.
- Less waiting after clicks.
- Improved perceived performance.
Prefetching is not the same as rendering.

Rendering produces UI, while prefetching prepares resources that may be needed later.
PART 23: What is Suspense?
Suspense is a React feature that allows you to display fallback content while a component is waiting for something.

Example:
import { Suspense } from "react";

function App() {

    return (
        <div>

            <h1>My Website</h1>

            <Suspense fallback={<p>Loading...</p>}>

                <ProductList />

            </Suspense>

        </div>
    );

}

If ProductList suspends while waiting for data or another supported resource, React can display:
My Website

Loading...

When the component is ready, React displays its actual content.
Suspense is useful for:
- Streaming.
- Lazy loading.
- Code splitting.
- Asynchronous component rendering.
- Loading states.
Important: Suspense does not automatically detect every ordinary asynchronous operation. Components and libraries must use Suspense-compatible mechanisms.
PART 24: What is Lazy Loading?
Lazy loading means loading something only when it is needed.

For example, imagine your website has 20 components.

You don't necessarily need to load every component immediately.

React provides lazy().
import { lazy, Suspense } from "react";

const Dashboard = lazy(() => import("./Dashboard"));

function App() {

    return (
        <Suspense fallback={<h2>Loading Dashboard...</h2>}>

            <Dashboard />

        </Suspense>
    );

}

Here:
import("./Dashboard")

loads the Dashboard module asynchronously when needed.

This is called code splitting.
Benefits
- Smaller initial JavaScript bundle.
- Faster initial loading.
- Better resource utilization.
PART 25: What is Code Splitting?
Code splitting means dividing your JavaScript application into smaller bundles.

Imagine your application contains:
Application
   |
   |-- Home
   |-- Dashboard
   |-- Products
   |-- Checkout
   |-- Reports

Without effective code splitting, the browser might need to download a large amount of JavaScript initially.

With code splitting:
Initial Bundle
     |
     |-- Home
     |-- Common Components

Separate Bundles
     |
     |-- Dashboard
     |-- Products
     |-- Checkout
     |-- Reports

The browser can load additional bundles when required.

This improves loading performance.

Next.js automatically performs various forms of code splitting based on routes and component boundaries.
PART 26: What is Selective Hydration?
Selective hydration is an advanced React concept.

Imagine your page contains:
Page
  |
  |-- Header
  |
  |-- Product List
  |
  |-- Reviews
  |
  |-- Footer

Some components may be more important for interaction than others.

For example:
- Add to Cart button is important.
- Reviews are less urgent.
- Footer might not need immediate interaction.
With Suspense boundaries, React can prioritize hydration work rather than treating the entire page as one indivisible unit.

This can improve responsiveness on complex pages.

It is particularly relevant to React's streaming server-rendering architecture.

PART 30: Common Misunderstandings You Should Avoid
These are important interview and practical development points.
1. Rendering does not always mean DOM updating.
React can execute a component again without making any DOM changes.
2. Virtual DOM is not the actual DOM.
Virtual DOM is an in-memory representation used by React.
3. React does not update the entire page after every state change.
It calculates the necessary updates and commits them.
4. Client Component does not mean CSR.
A Next.js Client Component can be server-pre-rendered on the initial page load.
5. Server Component does not automatically mean SSR.
Server Components can be rendered during build time or request time.
6. Hydration does not generate the initial HTML.
Hydration connects React to existing server-generated HTML.
7. SSR does not mean no JavaScript.
Client-side JavaScript is still required for interactive Client Components.
8. SSG does not mean the content can never change.
ISR and on-demand revalidation allow static content to be updated.
9. Reconciliation and Fiber are not identical.
Reconciliation determines UI changes. Fiber provides the architecture for managing rendering work.
10. useEffect does not execute on the server.
It runs on the client after the component has been committed.
